Implementation Inspection Checklist#

Purpose#

The purpose of this checklist is to collect the topics to be checked during implementation, i.e. in the detailed design and the source code of the units.

The checklist shall be agnostic to which programming language is used. Differences shall be treated by linking to C++ or Rust specific documentation.

Conduct#

As described in the concept doc_concept__wp_inspections the following “inspection roles” are expected to be filled:

  • content responsible (author): <contributor/committer explicitly named here, who is the main author, as can be seen in config mgt tooling>

  • reviewer: <contributor/committer explicitly named here, who is the main content reviewer, must be different from content responsible>

  • moderator: <committer explicitly named here, who is is the safety manager, security manager or quality manager initiating the inspection>

Checklist#

It is mandatory to fill in the “passed” column with “yes” or “no” for each checklist item and additionally to add in the remarks why it is passed or not passed. In case of “no” an issue link to the issue tracking system has to be added in the last column (if not solved in the same issue). See also doc_concept__wp_inspections for further information about reviews in general and inspection in particular.

IMPL_01_01

Is the design according to guidelines?

see gd_temp__detailed_design and doc_concept__imp_concept (e.g. are the views done with the proposed UML diagrams)

no

The detailed design consists of Rust Bridge Detailed Design and the stub Log Frontend Detailed Design. The C++ design is in score/mw/log/design and is not part of the documentation build, the bundle //score/mw/log:docs rejects files outside score/mw/log/docs (mounts.path_escape).

Following issues need to be addressed:

  • Move the C++ design into the documentation and restructure it after the template.

  • Add an architectural_design target that validates the diagrams.

  • Rust Bridge Detailed Design uses the architecture need types comp_arc_sta and comp_arc_dyn. log_to_level.puml refers to dd_dyn__log__log_op, which does not exist.

Design location: #187. Other points: To be added.

IMPL_01_02

Is the implementation according to specification?

Check if the linked component requirements are fulfilled and detailed design also matches architecture description.

no

29 existing tests were linked to 13 of the 18 component requirements. The requirement-to-test traceability is shown in Component Requirements Statistics.

Following issues need to be addressed:

  • No test for Message Loss Detection (comp_req__log__log_loss_detect), Local Timestamp (comp_req__log__timestamp_local), Console Backend Stdout Sink (comp_req__log__console_backend) and System Logger Backend (comp_req__log__system_logger). Compatibility Supported Ope... (comp_req__log__compat_os) and Compatibility Supported Pro... (comp_req__log__compat_languages) need another verification method.

  • Logging Configuration File ... (comp_req__log__cfg_file_loc) defines another search order than configuration/configuration_file_discoverer.cpp.

  • Logging Configuration Log E... (comp_req__log__cfg_log_ecu_id) and Logging Configuration Log A... (comp_req__log__cfg_log_app_id) require uppercase, the code does not check it.

  • The Rust tests have no requirement links.

To be added

IMPL_01_03

Are the design decisions and constraints documented?

Check also for plausibility of these.

no

Design decisions in design/README.md and design/design_decisions.md were checked against the code.

  • design/dependency_graph.md states that the frontend does not depend on the details, it uses detail:empty_recorder, detail:thread_local_guard, detail:logging_identifier and detail/wait_free_stack.

  • The constraints of the units (slot count, slot size, slots per drain cycle, queued slots) are not documented.

IMPL_01_04

Are all external libraries used by the component specified in the detailed design?

Check the automated dependency analysis. Also make sure ASIL rated units also only use ASIL rated libraries.

no

Dependency and FFI metadata are maintained in Bazel. The direct dependencies outside of the component are listed with:

bazel query "let l = kind('.*_library|rust_proc_macro',
  //score/mw/log/... + //score/log_rust/...)
  except attr(testonly, 1, //score/mw/log/... + //score/log_rust/...)
  in labels(deps, \$l) + labels(implementation_deps, \$l)
  + labels(proc_macro_deps, \$l)
  except (//score/mw/log/... + //score/log_rust/...)" \
  --output=label_kind

Following issues need to be addressed:

  • //score/json, //score/language/futurecpp and the crates syn, quote and proc_macro2 have no FFI tag and no stated rating.

  • The crates score_log, score_log_fmt, stdout_logger and stdout_logger_cpp_init have no FFI tag.

  • The external libraries are not listed in the detailed design.

  • The high_resolution_steady_clock target is deprecated and its replacement is not available in the open source dependencies.

To be added

IMPL_03_01

Do the UID of the interface in component documentation match the implemented interface names of the unit?

Compare interface UIDs (which contains the interface name) in component architecture/detailed design documentation with public interfaces in source code (e.g. API headers, traits, public types/functions).

IMPL_03_02

Are detailed design and source code consistent and is the respective traceability established ?

Check if available static and dynamic design diagrams and the textual descriptions match the code (e.g. naming of interfaces, units, functions/operations/messages, data types). Check if the folder/file names of the units and its source code matches the intended functionality. For example if a unit is named “communication” it should not contain code for “data processing”.

no

The C++ design in score/mw/log/design and Rust Bridge Detailed Design were compared with the code. The folder and file names of the units match their function.

Following issues need to be addressed when the design is moved into the documentation (see IMPL_01_01):

  • Classes that do not exist (RecorderFactory, ConsoleRecorder, RecorderComposite, namespace bmw::).

  • Sequences that differ from the code (recorder creation, fallback recorder, console output path).

  • The configuration design uses outdated names, a wrong class-id.json path and a wrong discovery order.

  • The slot drainer diagrams miss the mutex, the slot allocation shows one atomic operation as two steps.

  • Rust Bridge Detailed Design lists 3 of 5 crates, class_diagram.puml shows the crate score_log_subscriber that does not exist.

Design location: #187.
